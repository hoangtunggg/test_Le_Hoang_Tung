# Manual Test Plan: Critical Authentication and Todo Regression Scope

## 1. Scope & Objective

- Test objective: Manually validate critical authentication, authorization, data-isolation, todo CRUD, partial-update, and cache-consistency behavior.
- Test scope: Frontend user flows at `http://localhost:3000` and supporting API verification at `http://localhost:8000/api/v1`.
- Out of scope: Todo sharing, tags, bulk actions, load testing, and production infrastructure validation.
- Execution status: Executed on 2026-09-19 against the validated local Docker environment using fresh accounts, isolated browser contexts, direct API verification where specified, and authenticated Redis inspection for cache cases.

## 2. Test Environment & Prerequisites

- Start the application with the repository's Docker Compose configuration.
- Confirm the frontend is reachable at `http://localhost:3000` and the backend API is reachable at `http://localhost:8000`.
- Use a supported desktop browser in a clean browser context.
- Use an API client for cases that require direct HTTP status or partial-payload verification.
- Generate unique User A and User B email addresses for every execution, for example `manual-a-<run-id>@example.com` and `manual-b-<run-id>@example.com`.
- Use valid test passwords that satisfy the documented password policy. Do not record passwords, bearer tokens, or other credentials in test evidence.
- Use separate browser contexts or API sessions for User A and User B.
- For the expired-token case, use an isolated environment with a short access-token lifetime; do not change shared or production configuration.
- For cache cases, ensure Redis is enabled and the tester can confirm whether the relevant user-scoped list key exists.

Status notation:

- `PENDING`: Test has not been executed.
- `PASS`: Actual result matched the expected result.
- `FAIL`: Actual result differed from the expected result; record a defect reference.
- `BLOCKED`: Execution could not proceed; record the blocking reason.

Priority notation is execution urgency (`P0` highest). Severity describes user or security impact if the behavior fails.

## 4. Defect Tracking & Known Limitations

- Execution summary: 20 total, 20 passed, 0 failed, 0 not run.
- Invalid-login security behavior passed because known and unknown accounts produced identical status codes and generic response bodies. The frontend's global 401 redirect currently prevents the error toast from remaining visible after navigation; this is recorded as a UX limitation, not an account-enumeration failure.
- For a failed or blocked case, record the observed status code or UI behavior, execution environment, reproducible evidence, and defect identifier without storing credentials or raw tokens.
- Direct-object authorization cases use the API because the current UI does not expose navigation to an arbitrary todo ID.
- Cache cases require Redis inspection access to prove the cache was populated and invalidated rather than merely observing a fresh database response.
- The expired-token case requires an isolated short-lived-token configuration to keep manual execution practical.
- Existing automated backend and Playwright coverage complements this plan but does not count as manual execution evidence in the **Actual Result** column.
